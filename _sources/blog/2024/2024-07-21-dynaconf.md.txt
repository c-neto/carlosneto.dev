# Dynaconf: The Python Config Silver Bullet!

This blog post gives a short overview of good practices for application configuration, explains the main features of [Dynaconf](https://github.com/dynaconf/dynaconf), and walks through a hands-on example that extends it to read parameters from AWS Systems Manager Parameter Store.

## Twelve-Factor App: Good Practices for Application Config

Before talking about Dynaconf or any code, it helps to know the practices behind portable configuration.

The **Twelve-Factor App** is a methodology with a set of good practices for building modern applications that run anywhere, such as on SaaS platforms or Kubernetes clusters. It has a chapter dedicated to [configuration](https://12factor.net/config), which defines what counts as configuration (anything that changes between deploys, such as credentials and resource addresses) and insists on keeping it strictly separate from code.

## Python Config Libraries

Like most common needs with well-known practices, configuration has libraries to help. I have used a few good ones in Python:

- [python-dotenv](https://github.com/theskumar/python-dotenv) reads simple key-value pairs from a `.env` file and can export them as environment variables.
- [python-decouple](https://github.com/HBNetwork/python-decouple) gives you one settings interface so you can change parameters without redeploying the app, which is useful for web applications.
- Structured file parsers can also serve as config readers, such as [PyYAML](https://pyyaml.org/wiki/PyYAMLDocumentation), [json](https://docs.python.org/3/library/json.html#module-json), [tomllib](https://docs.python.org/3/library/tomllib.html#module-tomllib), [shlex](https://docs.python.org/3/library/shlex.html#module-shlex), and [configparser](https://docs.python.org/3/library/configparser.html).

These modules have their use cases, especially for simple scripts where the standard library is enough. But, as the provocative title suggests, this post is about Dynaconf.

## Dynaconf

**Dynaconf** is a configuration management library for Python, designed around the [Twelve-Factor config](https://12factor.net/config) principles. It sits between your code and your settings and gives you one interface to read parameters and secrets from files or external systems.

Its main features are:

- Multiple config files in several formats (_toml, yaml, json, ini_), merged into one settings object.
- Parameters from environment variables, which take precedence over files.
- Layered environments (profiles) such as _default, development, production_.
- A CLI that helps with debugging.

The feature I like most is reading parameters from external parameter and secret stores. Dynaconf has built-in support for HashiCorp Vault and Redis, and you can write your own loader for any other source. The example below does exactly that for AWS Parameter Store.

## Talk Is Cheap, Show Me the Code!

This step-by-step guide sets up Dynaconf from scratch with two settings files, then adds a custom loader for the AWS Parameter Store service. [LocalStack](https://github.com/localstack/localstack) simulates AWS in a Docker container, so you don't need an AWS account.

### Step-by-step


1. Create a virtual environment and install dependencies:

```bash
python3 -m venv venv
venv/bin/pip install dynaconf boto3 
source venv/bin/activate
```

2. Use the Dynaconf CLI to create the settings files and `config.py`:

```bash
dynaconf init \
    -v PARAMETER_FROM_SETTINGS_TOML_FILE="foobar from settings.toml" \
    -s PARAMETER_FROM_SECRETS_TOML_FILE="foobar from .secrets.toml"

# » output
#
# ├── config.py       » python module with dynaconf instance
# ├── .secrets.toml   » settings files with: PARAMETER_FROM_SECRETS_TOML_FILE
# └── settings.toml   » settings files with: PARAMETER_FROM_SETTINGS_TOML_FILE
```

_The `config.py` that the CLI creates looks like this:_

```{code-block} python
:caption: config.py

from dynaconf import Dynaconf

settings = Dynaconf(
    envvar_prefix="DYNACONF",
    settings_files=['settings.toml', '.secrets.toml'],
)
```

_The CLI can list the parameters that `config.py` loads:_

```bash
dynaconf -i config.settings list 

# » output
#
# PARAMETER_FROM_SETTINGS_TOML_FILE<str> 'foobar from settings.toml'
# PARAMETER_FROM_SECRETS_TOML_FILE<str> 'foobar from .secrets.toml'
```

3. Run LocalStack in a container to simulate the AWS Parameter Store service:

```bash
docker run --rm -it --detach \
    --name localstack \
    -p 4566:4566 \
    -e SERVICES=ssm,sts \
    -e DEFAULT_REGION=us-east-1 \
    -e AWS_ACCESS_KEY_ID=test \
    -e AWS_SECRET_ACCESS_KEY=test \
    localstack/localstack:latest
```

4. With LocalStack running, export the AWS environment variables that point to its API:

```bash
export AWS_ACCESS_KEY_ID=test
export AWS_SECRET_ACCESS_KEY=test
export AWS_ENDPOINT_URL=http://localhost:4566
export AWS_DEFAULT_REGION=us-east-1
```

5. Create two parameters under the `/my-application/` prefix, named `PARAMETER_FROM_AWS_PARAMETER_STORE_1` and `PARAMETER_FROM_AWS_PARAMETER_STORE_2`:

```bash
aws ssm put-parameter \
    --name "/my-application/PARAMETER_FROM_AWS_PARAMETER_STORE_1" \
    --value "foo" \
    --type "SecureString" \
    --endpoint-url http://localhost:4566

aws ssm put-parameter \
    --name "/my-application/PARAMETER_FROM_AWS_PARAMETER_STORE_2" \
    --value "bar" \
    --type "SecureString" \
    --endpoint-url http://localhost:4566
```

6. Edit `config.py` to add a custom loader that reads every parameter under `/my-application/` from AWS Parameter Store. A **Dynaconf loader** is a module with a `load()` function that Dynaconf calls to add values to the settings. If there is no AWS session, the code falls back to the environment loader only:

```{code-block} python
:caption: config.py

import logging

import boto3
from botocore.exceptions import ClientError, BotoCoreError
from dynaconf import Dynaconf, LazySettings
from dynaconf.loaders.base import SourceMetadata

logger = logging.getLogger(__name__)
PARAMETERS_PREFIX = "/my-application/"


# Retrieve parameters from AWS Parameter Store recursively by prefix
def _aws_parameter_store_loader(parameters_prefix: str) -> dict:
    ssm_client = boto3.client('ssm')

    paginator = ssm_client.get_paginator("get_parameters_by_path")
    pages = paginator.paginate(Path=parameters_prefix, Recursive=True, WithDecryption=True)

    parameters_from_aws_raw = {}

    for page in pages:
        for param in page["Parameters"]:
            name_full = param["Name"]
            value = param["Value"]
            parameters_from_aws_raw[name_full] = value

    parameters_from_aws = {}

    for name_full, value in parameters_from_aws_raw.items():
        try:
            *_, name = name_full.split("/")
        except ValueError:
            logger.warning(f'Parameter name pattern outside of expected format, skipping: "{name_full}"')
        else:
            parameters_from_aws[name] = value

    return parameters_from_aws


# Dynaconf callback - used in this case for retrieve parameters from AWS Parameter Store
def load(obj: LazySettings, env: str, silent: bool = True, key: str = None, filename: str = None) -> None:
    global parameters_from_aws

    source_metadata = SourceMetadata('aws-parameter-store', PARAMETERS_PREFIX)
    obj.update(parameters_from_aws, loader_identifier=source_metadata)
    logger.debug(f"Parameters loaded from AWS Parameter Store: {list(parameters_from_aws)}")


# Attempt to load parameters from AWS Parameter Store and update Dynaconf loaders
try:
    parameters_from_aws = _aws_parameter_store_loader(PARAMETERS_PREFIX)
except (BotoCoreError, ClientError) as e:
    LOADERS_FOR_DYNACONF = ["dynaconf.loaders.env_loader"]
    logger.warning("AWS active session not detected, skipping load parameters from AWS Parameter Store")
else:
    # __name__ is module name that have "load()" callback. It could be another module...
    LOADERS_FOR_DYNACONF = [__name__, "dynaconf.loaders.env_loader"]


# Initialize Dynaconf settings with specified files and loaders
settings = Dynaconf(
    settings_files=["settings.toml", ".secrets.toml"],
    envvar_prefix="MY_APP",
    LOADERS_FOR_DYNACONF=LOADERS_FOR_DYNACONF,
)
```

7. List the settings again. `PARAMETER_FROM_AWS_PARAMETER_STORE_1` and `PARAMETER_FROM_AWS_PARAMETER_STORE_2` now come from AWS Parameter Store:

```bash
dynaconf -i config.settings list

# » output
#
# PARAMETER_FROM_SETTINGS_TOML_FILE<str> 'foobar from settings.toml'
# PARAMETER_FROM_SECRETS_TOML_FILE<str> 'foobar from .secrets.toml'
# PARAMETER_FROM_AWS_PARAMETER_STORE_1<str> 'foo'
# PARAMETER_FROM_AWS_PARAMETER_STORE_2<str> 'bar'
```

8. Environment variables take precedence over every other source. To see it, export `MY_APP_PARAMETER_FROM_AWS_PARAMETER_STORE_2`:

```bash
export MY_APP_PARAMETER_FROM_AWS_PARAMETER_STORE_2="param from environment variable"
```

> Dynaconf only reads environment variables that start with the `envvar_prefix` value, `MY_APP` in this case.

_Now `PARAMETER_FROM_AWS_PARAMETER_STORE_2` returns the value from the environment variable:_

```bash
dynaconf -i config.settings list

# » output
# 
# PARAMETER_FROM_SETTINGS_TOML_FILE<str> 'foobar from settings.toml'
# PARAMETER_FROM_SECRETS_TOML_FILE<str> 'foobar from .secrets.toml'
# PARAMETER_FROM_AWS_PARAMETER_STORE_1<str> 'foo'
# PARAMETER_FROM_AWS_PARAMETER_STORE_2<str> 'param from environment variable'
```

## Why I Use Dynaconf

I have been using Dynaconf for about 4 years, and I like how it solves common configuration problems in a simple, direct way. Before, I used [PyYAML](https://pyyaml.org/wiki/PyYAMLDocumentation), but I kept writing the same code to read configuration and secrets from different files. When a mix of sources was needed, such as YAML and environment variables, the code grew more complex and pulled attention away from the problem the system was supposed to solve.

The first time I tried Dynaconf, its ability to merge several config files, including nested parameters, impressed me. It's especially useful for keeping sensitive values in their own file.

Today, I only skip Dynaconf when a project requires the standard library only. Otherwise, I don't see a reason not to use it, especially in applications that run on Kubernetes. I really like the module and suggest you give it a try!

If you write Python for operations work, two other posts may interest you: [groupby + attrgetter](/blog/2025/2025-07-28-python-groupby.md) for grouping objects without loops, and [OpenTelemetry](/blog/2026/2026-10-29-otel-foundation.md) for instrumenting a Python application.

## Key Takeaways

- The Twelve-Factor App says configuration is anything that changes between deploys, and it must live outside the code.
- python-dotenv, python-decouple, and file parsers such as PyYAML cover simple cases, but mixing sources with them means writing glue code.
- Dynaconf merges several config files and formats, environment variables, and environment profiles into one `settings` object.
- Environment variables with the configured prefix (`MY_APP_` in the example) override every other source.
- A custom loader is a module with a `load()` function, added to `LOADERS_FOR_DYNACONF`. The example reads every parameter under `/my-application/` from AWS Parameter Store.
- `dynaconf list` and `dynaconf inspect` show the final values and which loader set each one.
